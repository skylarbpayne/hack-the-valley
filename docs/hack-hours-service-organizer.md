# Hack Hours service organizer assignment (review-only; not activated)

This path does **not** authorize a production grant. It exists only to assign/revoke `organizer` for the `hack-hours` event on a single preapproved, existing HTV user. It cannot create users, choose a different event or person, grant global/admin rights, impersonate a session, or access D1 generally. It never uses `HTV_ADMIN_TOKEN` or a Cloudflare API key as application authorization.

## One-time deployment and activation boundary

1. Skylar explicitly approves the HTV PR merge/deploy separately. The production deploy migrates `0036_hack_hours_service_identity.sql`; until configured and activated the service route rejects all requests. No production settings or Access resources are changed by this PR.
2. An HTV/Cloudflare administrator creates a **dedicated** Cloudflare Access self-hosted application protecting only `/api/service/hack-hours-organizers` on the HTV domain, with a Service Auth policy restricted to one named service token (no broad user Allow policy). Enable Access JWT assertion forwarding. Set Worker nonsecret configuration `HTV_ACCESS_ISSUER=https://<team>.cloudflareaccess.com` and `HTV_ACCESS_AUDIENCE=<dedicated application AUD>` after checking both against the Access application. Never reuse an admin/shared token; keep the Access client secret solely in the operator's approved secret manager. Provisioning Access, changing Worker settings, and deploying all require separate HTV approval; this document is not authorization.
3. The administrator checks the intended target identity **in the HTV app** and `hack-hours` slug. For the current approved request, the target is `mofmofcool@gmail.com` only. A legitimate signed-in global HTV admin (not a bootstrap token) uses same-origin `POST /api/admin/hack-hours-service` with `{"action":"activate","client_id":"<Access service token client ID>","email":"mofmofcool@gmail.com"}`. This is a one-time admin-approved activation and auditable binding to the existing user ID. Read back the response and audit event. Do not automate this step from an inherited CLI account.
4. The independently authorized operator sends the Access service token headers to the **Access-protected** service path. `POST /api/service/hack-hours-organizers` accepts only `{"action":"grant","email":"mofmofcool@gmail.com"}` or `action=revoke`. `GET` reads back the active event-scoped role of that bound target. Confirm the event slug, exact role, target and audit source `hack-hours-service`; inspect `GET /api/dashboard` only in Mofe's own signed-in session if desired. Mofe changes his December event date himself; the machine route does not edit events.

The Worker verifies the Access-signed JWT against the configured team's rotating JWKS, issuer, dedicated app audience, expiry, service-token claim, and live per-client activation row. An Access header alone is insufficient. Do not share JWTs, client secrets, login links, passwords, or session tokens in source, chat, logs, or Skyvault.

## Rotation and revocation

Create a fresh Access service token and replace its Service Auth policy selection; activate the new client ID via a signed-in admin for the **same** target after explicit approval, verify, then revoke the old client ID with same-origin `POST /api/admin/hack-hours-service` (`{"action":"revoke","client_id":"<old ID>"}`) and read back audit/denial. Revoke/delete the old Access token in Cloudflare as well. Emergency stop: revoke the activation row first (blocks even an unexpired JWT), then revoke the Access service token/policy. Revoking the *machine identity* does not revoke an already granted human organizer role; a separate scoped organizer revoke (by a signed-in HTV admin or still-authorized machine) and role readback is required. Do not infer that rotation or revocation happened without both sides' readbacks.

## Local evidence and limitations

`node --test tests/service-organizer.test.mjs` uses a generated fixture RSA key, real SQLite migrations, synthetic HTV admin sessions, signed Access-like assertions and the Worker router. It exercises activation, grant/readback/revoke, wrong target/scope/role, invalid assertion, bootstrap denial, audit rollback, and identity revocation. It does not verify a live Cloudflare Access application, production grant, Mofe's login, or production identity provisioning. `npm run check` and `npm test` are the broad gates. No PR checks should be inferred if GitHub has none configured.
