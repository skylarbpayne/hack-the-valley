# Shared social logins (HTV)

`/shared-logins/` uses the existing magic-login session. Active **global** `admin` and `super_admin` roles confer implicit read and management access; the role is checked live on each request and again in the audited reveal/write SQL guard. A revoked admin role stops implicit access immediately, unless the same user still has an explicit active vault grant. Bootstrap API tokens, event-scoped roles, and organizer roles never grant vault access. Explicit `owner` grants retain read and management access; explicit `member` grants allow only list and reveal. A social manager therefore needs an explicit `member` grant and gains no event/admin rights. No HTTP self-enrollment exists.

The **15-seat limit counts distinct people** in the union of active global admins/super-admins and active vault owner/member grants. An admin who also has explicit membership counts once. Forward migration `0034_social_vault_effective_seats.sql` atomically rejects new member grants/reactivations and admin role grants/reactivations that would add a 16th effective person. It preserves all existing owner/member rows; it never silently deletes grants. Before approved migration/deploy, read-only check the current union count. If legacy data already exceeds 15, do not deploy as compliant: resolve the excess with an explicitly approved roster decision first. Revoking only an admin's explicit membership does **not** remove implicit admin access or free a seat; revoke the global admin role as well. Conversely, revoking admin leaves explicit membership intact. The count displayed in the vault includes both kinds of access.

`/organizer` is a narrow event-operations UI. Global or event-scoped organizers may update their event, check in existing signups, view event roster, and upload photos. They do not receive all-user lookup, badges, content, email/broadcast, sponsorship, physical-resource, audit, or role-management rights. `/admin` remains a full-admin console. Global admins can manage `admin` grants via `/api/admin/roles`; the separate `super_admin` bootstrap/seed path is not exposed there. Granting any role or vault membership is a separate, explicit operation: this code does not provision named people or modify the live roster.

## Approved deployment/onboarding boundary

1. Apply forward-only migrations and deploy only after explicit HTV approval. Migration `0033` creates the vault; `0034` enforces the effective seat union. No production data changes are part of this implementation.
2. Provision `HTV_SOCIAL_VAULT_KEY` as a Cloudflare Worker secret, never in source or tracked configuration. Generate 32 random bytes, base64-encode them, retain a secured recovery copy. Losing the key makes stored credentials unrecoverable; rotation requires replacing/re-encrypting stored credentials.
3. The first owner must sign in once, then be provisioned by an approved authenticated D1 operations session, looking up the exact `users.id` by email and inserting only that ID as `owner`. No email, ID, key, or password belongs in a migration or public issue. Read the owner row back.
4. Owners/admins can grant existing signed-in users in `/shared-logins/`. At 15 effective people, remove an effective seat before adding another. A role grant that exceeds the cap fails atomically.
5. After revocation, rotate every password the person might have seen at the social provider. Revocation cannot erase copied secrets.

Vault API responses are private/no-store. Reveal is a same-origin JSON POST audited before disclosure. Lists/audits do not contain login/password. Credentials use AES-256-GCM with a fresh 96-bit nonce and account ID as authenticated additional data. This is not a general-purpose password manager and cannot prevent an authorized person copying a credential.
